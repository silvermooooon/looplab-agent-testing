# Jira 浏览器集成交接

本文记录已确认的需求、现有代码约束和后续开发验收方式。Jira 集成处于待实现阶段，当前已有浏览器执行、人工接管、实时预览、项目用例及流程管理能力。

## 运行位置与交互方式

LoopLab 服务、Agent 执行器和自动化浏览器运行在用户本地电脑上。场内用户的电脑具备内网访问条件，用户在项目聊天中提供 Jira Ticket 链接即可发起任务。

Jira 的业务操作统一通过网页完成，包括打开 Ticket、读取 Story 和验收条件、查看评论、提交测试结果、上传证据以及调整状态。复用现有 Playwright 浏览器执行能力。接入的必需输入是 Ticket 链接和当前项目，认证通过用户在受控浏览器中的登录完成。

场外开发用本地临时模拟 Jira 验证交互和执行机制。场内 Agent 负责在真实 Jira 上确认页面结构、登录方式、编辑控件和状态流转，并完成真实验收。

## 分阶段执行与中间产物

每个阶段提供独立的脚本入口，由 Agent 按当前用户意图调用。下面的入口名称是开发约定，尚未实现。

| 阶段 | 建议入口 | 输入与产物 |
| --- | --- | --- |
| 读取需求 | `readJiraIssue` | 输入链接，输出从页面核对过的 Ticket 标识、标题、Story、验收条件、相关评论和采集时间 |
| 管理用例 | `saveTestCases` | Agent 根据需求整理用例，通过脚本保存到项目并关联 Ticket；返回保存版本 |
| 编排流程 | `composeTestFlow` | 读取用户选定的用例版本和测试环境，调查页面、复用节点，保存固定版本的流程 |
| 执行测试 | `runTestFlow` | 输入流程版本和环境，输出平台真实执行记录、断言结果和证据 |
| 回写结果 | `publishJiraResult` | 输入 Ticket 与明确的运行记录，在 Jira 页面发布结果，返回页面核验结果 |
| 调整状态 | `transitionJiraIssue` | 从当前页面读取可选转换，执行用户要求的转换，再读取实际状态 |

用户可以只要求生成用例，之后在管理页面反复编辑，再开启新对话要求生成流程。用户也可以先生成脚本，稍后运行，或另开对话单独回写已有结果。

项目中保存 Ticket 与用例、用例版本与流程版本、流程与运行记录、运行与 Jira 回写记录的关联。生成流程时读取用户当前选定的用例版本；后续手动编辑产生新版本，并提示已生成流程需要重新核对。新对话通过项目中的这些记录恢复任务。

Agent 负责理解意图、整理内容和检查执行结果。已有适配脚本优先执行；页面变化导致脚本失败时，Agent 调查实际页面，修复对应脚本或节点，再进行验收。脚本返回结构化结果和可定位的错误，界面显示所处阶段、实时画面和人工接管入口。

## 每个 Jira 脚本都要处理登录

所有 Jira 阶段共享一个“打开 Ticket 并确认登录”的前置能力，进入步骤和恢复步骤都使用它。登录检查以真实页面为依据。

1. 打开用户提供的链接，核对当前页面是目标 Ticket、登录页、权限错误页还是其他页面。
2. 已能读取目标 Ticket 时继续当前阶段。
3. 需要登录时保留当前浏览器上下文和页面，使用现有人工接管机制，请用户完成密码、验证码、MFA 或 SSO 登录。
4. 人工等待沿用现有暂停计时逻辑。已发出的浏览器操作仍可能达到自身超时，因此在读取、提交等动作之前检查登录状态。用户点击继续后，脚本重新检查登录结果；必要时导航回原 Ticket，并核对 Ticket 标识。
5. 仍处于登录页时再次请求接管。无访问权限、Ticket 不存在或网络不可用时，返回对应错误供 Agent 检查。
6. 登录在阶段中途失效时，从可核验的检查点恢复。如果评论提交或状态转换的结果不明确，先读取 Jira 页面核对是否已经生效，再决定是否重试。

以上是待实现的控制流程。当前节点的 `pauseForHuman` 可以暂停并继续，`watchElement` 可以在已知登录元素出现时暂停。登录判定、条件执行和恢复后的业务核验需要在 Jira 脚本层补齐，避免每次运行都无条件要求登录。

用户在同一个受控浏览器中完成登录，后续脚本继续使用该上下文。当前平台每次运行创建新上下文，跨运行的登录复用需另行实现。若加入本地登录状态缓存，应按本地用户和 Jira 站点隔离，凭据和浏览器认证状态保留在本机，项目共享数据库记录任务关联和结果。

脚本入口接受结构化参数，例如 Ticket 链接、用例版本、流程版本、环境和运行 ID。Agent 通过工具调用这些入口。Jira 页面选择器由场内调查确认，定位失败要保留现场、错误和已执行阶段，便于只修复相关操作。

## 回写与最终核验

回写使用明确的运行记录，包含所测用例、环境、执行时间、通过或失败结果和可访问的证据。用户只请求读取需求或生成用例时，任务在该阶段结束；用户请求回写或完整执行并更新时，按该范围执行后续阶段。

提交评论后，重新读取评论区域，核对内容和对应运行标识；状态转换后，读取页面状态。保存可从页面获取的评论标识或链接、运行 ID 和核验结果。对同一次运行重复回写前检查记录与页面，避免网络结果不明确时重复发布。Jira 中的证据链接必须能被场内读者访问；本机附件可通过页面上传到 Jira。

Jira 写操作使用单独的执行和回读核验。现有测试流程的“探索后再重放”会真实执行两次操作，若直接用于发布评论或转换状态，可能重复提交；需要在接入时明确写操作已经发生的位置，并让后续验收读取该结果。

## 场外临时模拟服务

使用 TS + Node.js 编写轻量页面服务，源文件、数据、启动日志和截图放在 `.data/jira-fixture/`。仓库已忽略 `.data/`，每次提交前用 `git status` 和 `git check-ignore` 确认临时文件的状态。

模拟服务只监听 `127.0.0.1`。开发时按需启动，结束后关闭；业务功能通过用户配置的 Jira 网页运行。

模拟页面至少覆盖以下交互：

- `/browse/DEMO-1` 展示 Story、验收条件、评论区和状态操作。
- 未登录访问跳转登录页，保留 Ticket 返回地址；登录后回到原页面。
- 可主动使会话过期，验证读取期间及提交前的重新接管。
- 评论提交后出现在页面，状态转换后能读取新状态，并可模拟提交后响应不明确的情况。
- 模拟无权限、Ticket 不存在、控件变更和操作失败，验证 Agent 能得到真实失败。
- 需要测试 SSO 时，用另一本机端口模拟登录站点，验证跨 origin 跳转和登录返回。

模拟页面的内部 HTTP 请求服务于页面交互。验收脚本通过浏览器访问这些页面，并在页面上核对结果。模拟站点通过仅说明本地控制流程成立，真实 Jira 的 DOM、富文本编辑器、SSO 和工作流还需场内验收。

## 接力顺序与验收条件

1. 场外先完成阶段入口、项目关联及版本管理、Jira 会话范围、人工登录恢复和 Agent 调用能力。
2. 用临时模拟站点完成端到端验证，记录已完成范围、证据和待场内确认项。沿用仓库约定，通过本平台验证功能，并做类型检查和构建。
3. 场内 Agent 使用实际 Ticket 链接调查页面，调整站点适配脚本，确认 SSO origin、弹窗、富文本输入和可用状态。
4. 场内逐项验收读取、生成用例、人工编辑、跨对话生成流程、独立运行、单独回写和状态调整，再验证用户明确要求的完整流程。

验收要包含一次人工登录后在原上下文继续操作、一次登录过期后的恢复、一次手动编辑用例后生成脚本、一次新对话回写旧运行结果，以及一次重复回写检查。每一阶段的成功以保存的业务产物或重新读取的页面结果为依据。
